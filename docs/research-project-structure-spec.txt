- plots          --> stores the plots resulting from plotting the data read by evaluations
- scripts        --> stores the scripts that launch the various scripts produced in code.
- shitpads       --> temp dir that could be useful to me or claude, its content is gitignored but the dir is present and can be useful.

- .env           --> stores .env stuff (see later for what it has to be stored there)
- .env.example   --> populated so as then one can fill the actual secrets
- README.md      --> repo readme, we will discuss what to put there
- CLAUDE.md      --> we will discuss what to put there
- JOURNAL.md     --> journal of what has been done, why, etc. in textual form. we will discuss what to put there and how, and also how to guarantee that it gets properly updated everytime we do something
- EXPERIMENTS.md --> tracks experiments todo, running, done in a precise way, i.e. the actual configs that are being ran, etc. we will brainstorm the structure later on.

first, we need to understand an important concept about an experiment, i.e. the run_id.

the run_id is what uniquely identifies a run of an experiment as far as the experiment config parameters are concerned.

the experiment config params that uniquely identify a run vary from experiment to experiment, from research project to research project.
so i want this to be defined crystal clearly everytime code for a new exp is being designed.
claude has to brainstorm with me about it. 
claude should NEVER decide which run parameters determine the run_id, i should always have the final say.
once the run_id is elected, it has to be stored somewhere.
this is point 1) that we have to brainstorm about... where and how to store the run_id.
This run_id identifies the experiments that we need todo, that are inpr, and that are done, and once is set it always identifies that run of that experiment.

you can think the run_id as a dict going from the config param name to the config param value, a string, a path or subpaths, or cells in a table...
it can be used in multiple ways, however its most appropriate to function as unique id for a run of an experiment.

from now on, we will refer to it as run_id and then refer to its "form" depending on the context.


each experiment will be assigned a name of the form NNN_[experiment name], where NNN is a three-digit zero padded number.
this is a generic rule, in some cases i might want something like NNN_[experiment name]/{NNN,NNN}_{[sub experiment name 1], [subexperiment name 2]}.
i.e. the atomic NNN_[experiment name] is always present, then i might have some sub exps, sub sub exps, etc.

each NNN_[experiment name], no matter what it's final form is, i.e. just one level or with sub-levels, will have a matching structure in code, configs, evaluations, plots, and scripts.
